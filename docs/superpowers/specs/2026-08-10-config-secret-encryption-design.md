# Config Secret Encryption Design

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:writing-plans to turn this spec into a task-by-task implementation plan.

**Goal:** Stop writing plaintext secrets (`db.password`, `jwt.secret`) to `appsettings.json` on disk.

**Architecture:** Add an AES-256-GCM layer around two config fields. Key lives in `.env` (sibling of `appsettings.json`), generated on first init. Loader detects per-value prefix `enc:v1:` and decrypts transparently; on startup, any plaintext values are auto-migrated to encrypted form (one-shot, atomic rename).

**Tech Stack:** Node `crypto` (built-in). No new dependencies.

## Global Constraints

- **No new deps.** AES-256-GCM via `node:crypto`.
- **Atomic writes.** All rewrites of `appsettings.json` go through the existing `writeConfig` atomic-rename path.
- **Fail-fast on key issues.** Missing `.env` key, mismatched key, or tampered ciphertext all abort startup with a clear error. Never silently fall back to empty/wrong password.
- **Backward compatible.** A plaintext `appsettings.json` from an older install must continue to load and trigger migration on first run.
- **Self-describing values.** Detection is per-value via prefix `enc:v1:`. No schema field or sidecar metadata file.
- **Agent config unaffected.** `agent/src/config.js` does not read `appsettings.json` and does not store DB credentials — out of scope.

## Format

Encrypted value string (one-line, stored as JSON string in `appsettings.json`):

```
enc:v1:<iv-hex>:<ciphertext-hex>:<tag-hex>
```

- `v1` — version prefix. Future algorithm/key-size changes can ship as `v2` and loader dispatches by prefix.
- `iv` — 12 random bytes (24 hex chars), generated per encryption.
- `ciphertext` — AES-256-GCM(plaintext, key, iv) ciphertext.
- `tag` — GCM auth tag (16 bytes / 32 hex chars).

Plaintext values stay unchanged — no migration needed for non-secret fields.

## Key Storage

`.env` (already exists for the init marker, written by `src/init/marker.js#writeMarker`):

```
EXDASHBOARD_INITIALIZED=1
EXDASHBOARD_SECRET_KEY=<64-hex-chars>   # 32 random bytes
```

- Random key generated by `crypto.randomBytes(32)` on first init.
- `.env` is git-ignored (project standard — verify in `.gitignore`; add if missing).
- Key never logged, never serialized to JSON, never returned by getters.

## Components

### New: `center/src/config/crypto.js`

Exports:

```js
isEncrypted(value) → boolean                                  // true iff value starts with "enc:v1:"
encryptString(plaintext, keyHex) → string                     // returns "enc:v1:<iv>:<ct>:<tag>"
decryptString(token, keyHex) → string                         // accepts plaintext OR "enc:v1:..."; throws on bad key/tag
loadOrCreateKey(envPath) → { key: string, created: boolean }  // reads .env; generates + writes if missing
```

Behavior:

- `decryptString` with plaintext input returns it unchanged (idempotent — supports in-flight migration where loader may see mixed values).
- `decryptString` with `enc:v1:` prefix + wrong key throws `Error('SECRET_KEY_MISMATCH')`.
- `decryptString` with `enc:v1:` prefix + tampered ciphertext throws (GCM tag mismatch).
- `loadOrCreateKey` preserves any existing `EXDASHBOARD_INITIALIZED` line, replaces/inserts `EXDASHBOARD_SECRET_KEY`, writes back atomically (tmp + rename).

### Modified: `center/src/config.js`

`loadConfigOrNull(configPath)` is extended to:

1. Read `.env` from `installPathFromConfigPath(configPath)`.
2. Read `appsettings.json`.
3. If `.env` missing key → throw `Error('MISSING_SECRET_KEY — set EXDASHBOARD_SECRET_KEY in .env')`.
4. Parse JSON, merge defaults (existing behavior).
5. For `cfg.db.password` and `cfg.jwt.secret`: if value starts with `enc:v1:`, decrypt; otherwise leave as-is.
6. Return `{ config, installPath, needsMigration: boolean }` — `needsMigration = true` iff any of the two fields was plaintext on read.

Backward compat: callers that destructure only `config` continue to work — `needsMigration` is an extra return field, not breaking.

### Modified: `center/server.js`

After `loadConfigOrNull` returns with `needsMigration: true`, and the wizard marker is locked (i.e. we're in post-init steady state), re-encrypt the two plaintext fields via `encryptString`, persist via `writeConfig`, log a single info line `"config secrets migrated to encrypted form"`.

Do **not** migrate during the wizard's `finalize` flow — wizard already writes encrypted (see below).

### Modified: `center/src/init/wizard-facade.js`

`finalize` step:

1. `loadOrCreateKey(envPath)` — generates and persists the key if this is a fresh install; no-op if reinstalling.
2. Generate `jwt.secret` as today.
3. Build `config` object, but pass the two secrets through `encryptString` before assigning.
4. Existing `writeConfig` + `writeMarker` flow runs unchanged.

Net effect: a fresh install never has plaintext `db.password` or `jwt.secret` on disk.

## Error Handling

| Condition | Behavior |
|---|---|
| `.env` missing `EXDASHBOARD_SECRET_KEY` | Throw `MISSING_SECRET_KEY`, center exits non-zero. UI shows error in healthz/boot logs. |
| `enc:v1:` value + wrong key | Throw `SECRET_KEY_MISMATCH`, center exits non-zero. Message tells user the `.env` key no longer matches `appsettings.json`. |
| `enc:v1:` value + tampered ciphertext | Throw on GCM tag verify, same exit path. |
| Plaintext secret during read | Auto-migrate on next startup (above). No error. |
| Plaintext secret during finalize | Encrypt before write (above). No plaintext ever written. |

Recovery guidance in the error message: "Restore the original `.env` (and registry marker if applicable), or re-run the wizard."

## Testing

### Unit: `center/tests/config/crypto.test.js`

- `encryptString` + `decryptString` roundtrip preserves plaintext
- `decryptString(plaintext, key)` returns plaintext unchanged (idempotent)
- `decryptString('enc:v1:bad...', key)` throws `SECRET_KEY_MISMATCH`
- `decryptString('enc:v1:...tampered', key)` throws (GCM tag failure)
- `loadOrCreateKey` on missing file → creates file with `EXDASHBOARD_SECRET_KEY=...` and existing marker line preserved
- `loadOrCreateKey` on existing file → returns existing key, no rewrite if value unchanged
- Two `encryptString` calls produce different output (random IV)

### Integration: `center/tests/config/load-migrate.test.js`

- Write a plaintext `appsettings.json` + missing `.env` → `loadConfigOrNull` throws `MISSING_SECRET_KEY`
- Write a plaintext `appsettings.json` + existing `.env` key → `loadConfigOrNull` returns decrypted config with `needsMigration: true`; calling the migration helper writes an encrypted file; second load returns decrypted values with `needsMigration: false`
- Write an already-encrypted `appsettings.json` → `loadConfigOrNull` returns decrypted config with `needsMigration: false`, file unchanged on disk (byte-equal)
- Tamper one byte of an `enc:v1:` value → `loadConfigOrNull` throws

### Existing tests

- All 118 existing center tests must continue to pass. The default `cfg.db.password = ''` and `cfg.jwt.secret = ''` paths are already handled (empty strings are valid plaintext — neither triggers the `enc:v1:` prefix).
- Init-wizard tests (`tests/init/wizard-facade.test.js`) must pass with encrypted write.

## Out of Scope

- Key rotation / multi-key support (add `v2` if ever needed)
- OS keychain / DPAPI integration
- Agent-side secret handling (agent has no DB credentials)
- UI surface for managing the key (recovery via wizard re-run only)
